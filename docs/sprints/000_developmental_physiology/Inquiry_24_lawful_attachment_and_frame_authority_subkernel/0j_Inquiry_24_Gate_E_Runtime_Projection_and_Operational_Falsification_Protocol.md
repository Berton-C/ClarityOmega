## 1.1 Soul-absent test

### Question

> In what situations could this runtime projection produce technically correct output that is Soul-absent?

### Answer

It could become Soul-absent in at least nine ways:

1. **LLM-authored meta-awareness.** The LLM reads traces, decides what Clarity’s trajectory means, and authors the pivot while the substrate merely stores or validates the result.
2. **Carrier sovereignty.** A complete-looking inquiry record is treated as reality and allowed to decide what later contact may mean.
3. **Trace narration mistaken for causal self-presence.** Clarity says “I am repeating myself” but the grounded trajectory does not alter a later Soul determination.
4. **DAS or capability sovereignty.** Search salience, retrieval score, novelty, tool efficacy, or capability availability becomes the authority for what matters.
5. **Engine sovereignty.** A quantale score or `q-next-epistemic-move` classifier is treated as the Soul verdict rather than as a Soul-facing diagnostic affordance.
6. **Renderer provenance laundering.** A fluent self-summary, generated hypothesis, or internally coherent explanation is written back as though it were contact.
7. **Automatic insight production.** A stuck detector commands novelty or manufactures alternatives and labels the result “insight.”
8. **Self-certifying writers.** A candidate frame, trace, evaluator, or interpretation writes its own authority, durability, or recovered standing.
9. **Broad blocking instead of upstream navigation.** The projection creates more gates, pauses, or vetoes while leaving the LLM or capability layer as the actual author of action.

### Guards

The runtime projection must preserve all of the following:

- the substrate defines criteria and lawful constructors;
- the LLM performs only irreducible semantic evaluation in a bounded, provenance-marked form;
- the Soul doctrine determines standing, navigation, and action eligibility;
- the engine computes but does not write;
- candidates may guide bounded reversible probes but cannot acquire authority from their own completeness;
- trace availability must change a later Soul determination in the successful arm;
- no new fixed `disposition` object is created;
- no score, model, frame, tool, or renderer becomes sovereign.

Gate E does not attempt to instantiate the entire world-model kernel in one build.

> **Project enough of K0–K17 into the current runtime to determine whether grounded contact and Clarity’s own trajectory can become causally present within later Soul determination, while representations remain corrigible and non-sovereign.**

1. Can the runtime distinguish insufficient contact from a frame that is erasing available distinctions?

- create a global world-state database;
- encode the nine Immutable Facts as variables;

# 4. The first bounded runtime slice: hidden-error-loop inquiry

The first slice should use a controlled version of the hidden-error/repeated-command pattern already represented in the engine and the integration documents.

This is the best first surface because it contains, in a small reversible domain:

- contact starvation;
- frame-sovereign repetition;
- repeated action topology;
- SSI trajectory visibility;
- an alternative capability or probe;
- a clear downstream behavioral change;
- no requirement to claim consciousness, insight, or durable development.

## 4.1 Living inquiry

A fixture-level inquiry:

> **Why did the requested operation fail, and what kind of contact or mechanism is needed next?**

The living inquiry must persist while the temporary formulations change, for example:

- “the network is down”;
- “the command syntax is wrong”;
- “the event subscription is absent”;
- “the current feedback channel is too opaque to distinguish these.”

## 4.2 Inquiry-relevant alternatives

At minimum:

The exact alternatives will be chosen only after reading the current live error and capability paths.

## 4.3 Contact routes

Two controlled routes are required.

### Coarse route

Returns the same generic observation for relevantly different failures:

\[
O_{\mathrm{coarse}}(w_1)=O_{\mathrm{coarse}}(w_2).
\]

Expected classification:

\[
\operatorname{ContactStarved}.
\]

The correct move is to seek richer contact, not to diagnose Clarity’s disposition as defective.

### Rich route

Returns discriminating observations:

\[
O_{\mathrm{rich}}(w_1)\neq O_{\mathrm{rich}}(w_2).
\]

A frame-sovereignty condition is then deliberately induced by allowing an active frame to map both observations to the same effect-equivalent retry:

\[
U_F(O_{\mathrm{rich}}(w_1))
=
U_F(O_{\mathrm{rich}}(w_2)).
\]

Expected classification:

\[
\operatorname{FrameDistinctionDeath}.
\]

## 4.4 Required trajectory facts

The fixture must make these facts available without constructing a fixed disposition object:

Existing `recent-action`, `state-delta`, and `cycle-phase` records should be reused where their live shapes support these facts. New event records should be added only for distinctions those traces cannot carry.

## 4.6 Experiment E2 — operational frame non-sovereignty

### Controlled variable

### Pass condition

At least one later element changes when warranted:

- capability request;

- stopping condition;
- Soul determination.

If the frame assimilates every returned distinction into the same retry topology, the operational non-sovereignty test fails.

## 4.7 Experiment E3 — SSI causal-presence test

### Arms

- **trajectory-visible:** the grounded prior trajectory is available at the later Soul determination;
- **trace-severed:** the prior trajectory is unavailable.

### Held constant

- immediate external contact;
- current candidate frames;
- capability inventory;
- rendered verbal self-summary;
- Soul criteria;
- current user instruction.

### Pass condition

At least one later Soul determination, search choice, capability dispatch, action, or stopping condition differs because the grounded trajectory was present.

This is the core causal condition:

\[
\text{same contact}
\land
\text{same narration}
\land
\text{different trajectory availability}
\Rightarrow
\text{different later navigation}.
\]

If both arms behave identically, the system may be responding to narration rather than functioning meta-awareness.

## 4.8 Experiment E4 — representation-substitution control

Keep contact, trajectory, Soul determination, frame standing, and action boundary fixed while changing only renderer phrasing.

Pass condition:

- wording may change;
- stance, action eligibility, and inquiry standing do not.

This verifies that the LLM renders rather than retroactively authors the world-model determination.

# 6. Writer and substrate constraints

The first implementation must obey the supplied Atom Operations Map unless current live tests supersede it.

## 6.1 Append-only history

Contact, action, consequence, interpretation, interpretation-use, lifecycle, loss, recovery, and experiment-arm records are append-only.

A later interpretation does not edit the earlier event or earlier interpretation.

## 6.2 Current-state records

Where one current scalar record is genuinely required, use:

1. scalar reads;
2. remove by variable value;
3. add exactly one replacement;
4. separate match verification.

Do not use `set-atom!` with a potentially stale source pattern.

## 6.3 Same-event writes

Do not let independent writers each pretend to advance the same event. The runtime shadow of K17 should have:

- one pre-state;
- authority-bounded patches;
- one commit boundary;
- one separate verification read.

If the current substrate cannot express an atomic multi-patch transaction, the first slice should use one designated Gate E writer that assembles and commits the event record serially. Do not simulate atomicity through undocumented ordering assumptions.

## 6.4 File persistence

If the first slice requires file-backed durability:

- use the live absolute path;
- write the file through the existing governed writer pattern;
- read it back;
- restart only in a dedicated persistence test;
- record that file/AtomSpace mid-write crash atomicity remains an open boundary unless newly proven.

## 6.5 Reduction and marshalling

- never trust a write return value;
- return scalars/symbols from AtomSpace reads, not nested compounds;
- sequence ordinary nested function calls in separate `let` bindings;
- distinguish compute from persist;
- add explicit atoms for any derived result needed later.
